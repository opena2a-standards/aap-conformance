# aap-conformance

Conformance fixtures and reference verifiers for the
[Agent Authorization Protocol (AAP) 0.5.0-draft](https://github.com/opena2a-standards/agent-authorization-protocol)
token canonical form (AAP-SPEC §9: JWTs over JWS — serialization IS
canonicalization).

Each fixture is a byte-stable JSON file that bundles a pinned AAP token
(AIT, CGT, DA, or BAC; compact or JWS General JSON Serialization) with
verifier configuration (a fixed clock, trusted keys, and where the fixture
needs them a path suite policy, the delegator's token, and the presenter's
proof) and an expected outcome (ACCEPT or REJECT with a pinned reject
category). Two SDK-independent reference verifiers (Node and Python) walk
the fixture set and report PASS or FAIL per vector. Fixture bytes are pinned
in [`MANIFEST.sha256`](./MANIFEST.sha256).

Run it:

```bash
npm install   # @noble/post-quantum, for the ML-DSA-65 fixtures (RFC 9964)
node verifiers/node/verify.mjs fixtures
# summary: 43 pass, 0 fail (43 fixtures)

pip install -r verifiers/python/requirements.txt
python3 verifiers/python/verify.py fixtures
# summary: 43 pass, 0 fail (43 fixtures)
```

The verifier pair is Node + Python deliberately (the
[a2a-idf-conformance](https://github.com/opena2a-standards/a2a-idf-conformance)
precedent, not the Go pair of atp-conformance): the AAP reference broker
([Secretless](https://github.com/opena2a-org/secretless-ai), `src/broker/cpi/assertion.ts`)
is TypeScript, so the Node verifier exercises the same `node:crypto` JOSE
primitives the reference mints with, and the Python verifier mirrors the
spec repo's fixture generator from the verification side.

This suite is the fifth in the family, alongside
[atx-conformance](https://github.com/opena2a-standards/atx-conformance),
[atp-conformance](https://github.com/opena2a-standards/atp-conformance),
[aip-conformance](https://github.com/opena2a-standards/aip-conformance), and
[a2a-idf-conformance](https://github.com/opena2a-standards/a2a-idf-conformance).

License: Apache 2.0. All key seeds in this repository
([`vectors/test-keys.json`](./vectors/test-keys.json)) are PUBLISHED TEST
KEYS for fixture reproduction only — never production use.

## Fixture provenance: reuse, not re-derivation

The ACCEPT fixtures embed the spec repo's published token bytes UNCHANGED —
the tokens generated by
[`agent-authorization-protocol/scripts/generate_examples.py`](https://github.com/opena2a-standards/agent-authorization-protocol/blob/main/scripts/generate_examples.py)
and embedded in AAP-SPEC §9.7. CI byte-compares them (and the vendored
schemas and test keys) against a pinned agent-authorization-protocol ref, so
this suite and the spec cannot drift apart silently. The REJECT fixtures are
single-defect variants minted by
[`scripts/generate-fixtures.mjs`](./scripts/generate-fixtures.mjs) with the
same construction: fixed clock, fixed jti values, published seeds —
deterministic and reproducible byte-for-byte.

Each negative fixture is valid in every respect except the one defect it
pins, so a verifier that skips that verification step (and only that step)
wrongly ACCEPTs it. Expected outcomes pin the reject category
(`MALFORMED_HEADER`, `UNKNOWN_HEADER_PARAM`, `UNKNOWN_ALG`, `BAD_SIGNATURE`,
`CLAIM_SCHEMA`, `CRIT_UNLISTED`, `CRIT_NOT_UNDERSTOOD`, `EXPIRED`,
`TTL_WINDOW`, `CNF_MISMATCH`, `DELEGATOR_INVALID`, `SCOPE_NOT_SUBSET`,
`NOT_ATTENUATED`, `HYBRID_INCOMPLETE`, `REPLAYED_JTI`), so rejecting for the wrong reason also
fails. Both verifiers implement the same pinned check order, documented at
the top of each verifier. AAP-SPEC names `REPLAYED_JTI` (§8.1) and
`HYBRID_INCOMPLETE` (§9.4) as conformance categories; the other names are
this suite's vocabulary for the rule each fixture cites.

AAP-SPEC 0.5 coverage: `authorization_details` (§4.4, RFC 9396) with the
§4.4.1 entry type registry, `aap_crit` (§4.5), `cnf` (§4.6, RFC 7800)
verified against a presenter proof (and rejected without one), the §5.4
attenuation relation over a DA's `authorization_details` together with
`trust_class`, the end of the validity window (`exp`) and `max_depth` (a
terminal, depth-0 delegation is accepted and delegating past it rejects),
the L3 `session_label` (§6.4), and the §9.4 family signature gate under a
per-path suite policy. Of the §5.4 relation, what the fixtures exercise is
the allow set member kind on a `data` entry (`fieldsAllowed`, rejected when
widened), the §5.5 `data` and `budget` entries accepted as narrower than the
§4.7 grant, and `max_depth`; the other member kinds and entry types are
implemented in both verifiers but not pinned (see the list below). The
presenter proof is the suite's fixture-input model of the broker profile
§6.8 signed-challenge binding, built deterministically (the challenge is
SHA-256 of a fixed label; the proof is the presenter key's Ed25519 signature
over those bytes and carries the presenter's public JWK, which the verifier
binds to the token through its RFC 7638 thumbprint); channel binding,
freshness and single use of the challenge are broker state and not
exercised.

Two parsing rules are load-bearing and deliberately asymmetric:

- The **protected header is strict-parsed**: duplicate members at any depth
  reject (`MALFORMED_HEADER`). v1 headers are closed (§9.2), and duplicate
  members are the classic last-wins/first-wins verifier split — the
  `duplicate-header-member` fixture pins that both verifiers agree
  (the atx-conformance Go/Python divergence lesson, applied here to JOSE).
- The **claim set parses with standard last-wins JSON semantics**, which
  RFC 7519 §4 explicitly permits and which `JSON.parse` and Python
  `json.loads` implement identically.

Post-quantum coverage (added with AAP-SPEC 0.4, RFC 9964): the suite carries real
ML-DSA-65 signatures — a compact PQ-interop ACCEPT fixture, a hybrid
Ed25519 + ML-DSA-65 General JSON ACCEPT fixture, hybrid negatives (either
half's signature corrupted MUST reject; a stripped hybrid missing the
Ed25519 family rejects `HYBRID_INCOMPLETE`), and an `ML-DSA-44` header
fixture pinning that JOSE-registered-but-not-AAP-registered suites reject
`UNKNOWN_ALG`. §8.1 replay prevention is fixture-tested too: presenting the
same token twice rejects `REPLAYED_JTI`. ML-DSA-65 fixture bytes are FIPS 204
deterministic signatures cross-verified by three independent implementations
(dilithium-py in the spec repo's generator, @noble/post-quantum here, OpenSSL
via Node ≥ 25). The verifiers take one PQ dependency each — `npm install`
(@noble/post-quantum) for Node, `dilithium-py` for Python — Ed25519 stays on
node:crypto / cryptography.

What this suite does NOT verify:

- §8.2 key exchange (hybrid X25519 + ML-KEM-768): transport key negotiation,
  not token wire form; ML-KEM has no final JOSE registration yet.
- Broker-profile runtime behavior (CPI endpoints, grant references,
  revocation propagation, the §7.3 grant revocation list): protocol flows
  and broker state, not token wire form. The grant-reference ABNF is
  validated in the spec repo's own CI.
- §8.3 intent verification and the optional-to-ignore CGT members
  (`intent_verified`, `context_required`, the deprecated `fga_constraints`
  and `max_uses`): the v1 reference does not mint them.
- The §4.4 narrowing rule between `authorization_details` and the scope
  string: the mapping from an OAuth scope string to the locations and
  actions it permits is deployment-defined, so it is not mechanical from the
  token alone. The §5.4 attenuation relation, which is mechanical, is pinned.
- The §6.8 presentation bindings other than the signed challenge (local
  socket peer credentials, RFC 9421 HTTP message signatures), and the
  channel properties of the signed challenge itself: channel binding,
  freshness and single use of the challenge are broker state and not
  exercised; the suite pins key binding (RFC 7638 thumbprint against `cnf`)
  and the signature over the challenge.
- The §4.5 producer rule that `aap_crit` MUST NOT name a §4.2 baseline
  claim: a producer MUST NOT with no verifier MUST; the verifiers reject such
  a name only as one they do not implement, and no fixture pins the rule.
- §5.4 for a DA that omits `authorization_details` while its delegator
  carries some: the spec's mechanical text quantifies over the entries a DA
  carries and is vacuous over an absent claim, so the verifiers pass it,
  while §4.4 reads a token without the claim as an unconstrained baseline
  token. A spec text gap; a fixture follows the spec sentence.
- §5.4 member kinds and §4.4.1 entry types no fixture exercises: identity,
  deny set, bound (`spend`, `rate`, `tokenCap`), restriction flags and
  constraint objects; `mcp_tool`, `skill`, `peer_agent`, `model` and
  `network` (including `*.` destination coverage). Implemented in both
  verifiers, not pinned.
- §5.4 start-of-window ordering (DA `iat` against the delegator's `iat`):
  not stated by the spec and bounded only by the family clock-skew bound
  (ATP §10.2, via broker profile §6 step 2), so it is not a verifier rule
  here; only the end of the window (`exp`) is checked and pinned.

The full requirement-to-fixture mapping is machine-readable in
[`conformance.json`](./conformance.json), regenerated from the fixtures by
[`scripts/conformance_profile.py`](./scripts/conformance_profile.py) and
CI-checked against drift.

## Continuous verification

[`.github/workflows/conformance.yml`](./.github/workflows/conformance.yml)
enforces every claim in this README on each push and pull request:

1. Both reference verifiers run against `fixtures/` and must report
   `43 pass, 0 fail`.
2. Schema validation
   ([`scripts/schema_validation.py`](./scripts/schema_validation.py)): every
   fixture's decoded header/claims/container must match its DECLARED schema
   validity against the AAP-SPEC schemas, vendored under
   `schemas/vendor/agent-authorization-protocol/` (some REJECT fixtures are
   claim-schema defects by design, so validity is declared per fixture, both
   directions gated).
3. Spec drift gate: the vendored schemas, the reused ACCEPT token bytes, and
   `vectors/test-keys.json` are byte-compared against a pinned
   agent-authorization-protocol ref
   ([`scripts/spec_pin_check.py`](./scripts/spec_pin_check.py)).
4. The fixture generator re-runs and the committed fixture bytes plus
   `MANIFEST.sha256` must reproduce exactly (byte-pin).
5. The cross-implementation parity gate
   ([`scripts/parity/parity.py`](./scripts/parity/parity.py)) asserts the
   Node and Python verifiers agree per fixture on gate status, verdict, and
   reject category, and publishes `parity-report.json` as a CI artifact.
6. `conformance.json` must match the fixture set.
7. On every push to `main`, CI keyless-signs `MANIFEST.sha256` with Sigstore
   cosign (Rekor is the durable record) — see
   [`COSIGNERS.md`](./COSIGNERS.md) for how second parties cosign.

## Using the fixtures against your own implementation

The fixtures are implementation-neutral: read a fixture, feed
`token` (compact) or `tokenGeneral` (JWS General JSON Serialization) to your
verifier configured with `verifierState.keys` (Ed25519 OKP and ML-DSA-65
AKP public JWKs) and `verifierState.clockNumericDate`, and compare your
verdict with `expected`. Where present, `verifierState.requiredSuites` is
the path's suite policy (§8.2) for a general-form token;
`delegation.delegatorToken` carries the immediate delegator's token (a CGT,
or a DA deeper in a chain) for the §5.2-§5.4 re-check — it is the delegator
only if its `sub` equals the DA's `act.sub` and, for a DA delegator, its
`act` equals the DA's `act.act` (RFC 8693 §4.1); a token that is not that
grant rejects `DELEGATOR_INVALID`, since checking it would re-check nothing;
and `presentation.proof` carries the presenter's signed-challenge proof
(`binding`, `challenge`, `jwk`, `signature`) for a token with `cnf`, which
rejects `CNF_MISMATCH` when the proof is absent or does not bind. A
conforming verifier matches the expected verdict on all 43 fixtures — and
rejects for the pinned reason, not just any reason.
